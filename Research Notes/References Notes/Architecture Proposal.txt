- Vietnamese dataset
- Split into 2 vector storages (Heart and Diabetes)
- Naive RAG baseline , and advanced RAG with simple pre-retrieval and 
post-retrieval.
- Pre-retrieval
+ metadata

- Retrieval

- Post-retrieval
+ relevance filtering
+ reranking
- RAGAS, Recall@k for evaluation.
- LangChain for agents.

# Workflow
1. User query
2. Query Agent: Check whether the question is related to healthcare and
medical, identify whether is about Heart or Diabetes before transforming
the query accordingly, determines whether to select Heart Retriever or
Diabetes Retriever or both.
3. RAG
4. Retrieval Verification Agent: "Does each retrieved passage contain 
information relevant to answering the user's question?" using an LLM 
for reasoning. If unsatisfied, rewrite the query before going back to 
step 3 (maximum N times), then combine them for final answer.
5. Generate
6. Answer Verification Agent:  
+ Is the answer relevant to the question?
+ Are its claims supported by the retrieved evidence?
+ Does it contain unsupported/hallucinated information?
-> If not then go back to step 5 (maximum N times).
7. Final answer.


# Polished plan
- The big picture: a question comes in, gets checked and routed, 
relevant info gets pulled and double-checked, an answer gets written 
and double-checked, then it's shown to the user. Every "double-check" 
step can send things back to be redone, up to N times, so a bad 
answer doesn't just slip through.

## Dataset
- Vietnamese-Healthcare (urnus11/Vietnamese-Healthcare)
- vietnamese-medical-qa (hungnm/vietnamese-medical-qa)

## Multi Vector Stores
- Starter: 2 vector stores covering Heart and Diabetes.
- Same embedding model, same chunking config for both.
- Store as two Qdrant/Chroma collections in the same instance (heart_kb
, diabetes_kb)

## Overview Pipeline:
1. User asks a question.
2. Query Agent reads the question and decides three things:
+ Is this actually about heart disease or diabetes? (if not, refuse 
politely)
+ Which one heart, diabetes, or both?
+ Rewrite the question to be clearer/more search-friendly (e.g. fix 
vague pronouns, expand abbreviations)
3. Retrieval searches the right knowledge base(s) for chunks of text 
that might answer the question. Two things happen here:
+ Before searching: the text is chopped into well-organized chunks 
with labels (metadata) so search has clean material to work with.
+ During searching: an embedding model finds the top k (~10) most 
similar chunks, then a second pass filters out the weak ones and 
reranks the rest so only the best 3-5 remain.
4. Retrieval Verification Agent asks: "do these chunks actually contain
what's needed to answer the question?". If not enough of them do, it 
rewrites the question and sends it back to step 3 to search again (up 
to N times).
5. Generate. the LLM writes an answer using only the retrieved chunks 
as its source material.
6. Answer Verification Agent checks the answer three ways:
+ Does it actually answer what was asked?
+ Is every claim backed by the retrieved chunks?
+ Is there anything made up (hallucinated) with no backing at all?
-> If it fails, send it back to step 5 to regenerate — up to N times.
7. Final answer shown to the user.

# Pipeline Detail
## RAG
### Pre-retrieval
- Chunking: Use underthesea for vietnamese-aware chunking 
(https://github.com/undertheseanlp/underthesea)

- Metadata schema:
{
  "doc_id": str,
  "disease": "heart" | "diabetes",
  "source": str,          # domain or hospital name
  "source_type": "qa" | "clinical_guideline",
  "section": str | null,  # e.g. "triệu chứng", "điều trị"
  "publish_date": date | null,
  "chunk_index": int
}

### Retrieval
- Embedding model: bkai-foundation-models/vietnamese-bi-encoder
- VectorDB: Qdrant with cosine similarity
- Hybrid retrieval (consideration): dense (bi-encoder) + sparse (BM25 
over the segmented text) combined via reciprocal rank fusion.

### Post Retrieval
- Reranking: BAAI/bge-reranker-v2-m3 (multilingual capability)
- Relevance filtering (consideration): score each of the 10 candidates 
against the question (via a smaller model or LLM judgment) and drop the
weak ones.

## Agentic
- Uses LangGraph
- Graph nodes → conditional edges:
+ query_agent → route_domain → retrieve
+ retrieve → verify_retrieval
+ verify_retrieval (if unsatisfied AND retries<N)--> rewrite_query → 
retrieve
+ verify_retrieval (if satisfied OR retries==N)--> generate
+ generate → verify_answer
+ verify_answer (if unsatisfied AND retries<N)--> generate  (regenerate
w/ feedback)
+ verify_answer (if satisfied OR retries==N)--> final_answer
- N = 2

# Evaluation
- RAGAS:
+ Context Precision: are retrieved chunks actually relevant (validates 
post-retrieval filtering).
+ Context Recall: did retrieval get everything needed (validates 
chunking/embedding choice).
+ Faithfulness: is the answer grounded in context (validates Answer 
Verification Agent).
- Eval set construction: ~50-100 hand-written or curated Q&A pairs.
